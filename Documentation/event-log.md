Append an event to record what happened, then decide whether you need to wait for its consequences. Chronicle's event log is its primary [event sequence](/chronicle/events/). Start with a connected event store and a [registered event type](./event-types.md); [TypeScript client setup](./getting-started.md) covers both. For a non-local server, complete the [connection security setup](./connecting.md#secure-the-connection-with-tls) first.

Call `eventStore.eventLog.append(eventSourceId, event)` with the ID of the source the event belongs to. For an order, that might be `order-123` and an instance of your registered `OrderPlaced` class. The ID groups that order's events; it is not the event type. [Appending events](/chronicle/events/appending/) shows the shared workflow, and [Event sources and streams](./event-sources.md) explains optional named routing.

Inspect the returned `AppendResult.isSuccess` before doing anything that assumes the event was stored. A constraint violation, concurrency violation, or append error is returned in `constraintViolations`, `concurrencyViolation`, or `errors`; it does not automatically throw. Prevalidation and transport failures can still reject the append call. For [a batch](/chronicle/events/appending-many/), `appendMany` returns one result per event, so check each result.

An accepted append does not mean a reactor, reducer, or projection has finished processing it. In a script or test, you can wait on that accepted result with `waitForCompletion()`: inspect `completion.isSuccess` and `completion.failedPartitions`, and handle rejection separately. A timeout or cancellation stops the wait, not the append. Do not append the event again just because the wait ended. The [failed-partitions example](./failed-partitions.md#waiting-for-completion-instead-of-polling) shows these branches together. If you then need current state, [read the model and handle absence](./read-models.md); a successful wait does not promise that a particular model/key exists.

## TypeScript client notes

- An append without route options leaves the route to the kernel. Clients before this change sent a `Default` route themselves, so existing streams need attention; follow [Preserve existing append routes](./migrate-append-routing.md) before upgrading.
- `AppendOptions` accepts `sourceType`, `streamType`, `streamId`, `subject`, `occurred`, `correlationId`, `tags`, `namedTags`, `concurrencyScope`, and `concurrencyScopes`. Rich batch entries override shared metadata; concurrency scopes remain independent.
- Structured named tags are `NamedTag` values: a nonblank name and an exact, possibly empty, value. Pass them as `namedTags` on `AppendOptions` (shared by every event) or on an `EventForEventSourceId` entry (that event only). Each event gets its own tags first, then the shared ones, keeping the first occurrence of each exact name and value pair. An invalid tag throws `InvalidNamedTag` before anything is sent. An append that carries named tags uses the kernel's dedicated named-tag call, so a kernel without named-tag support rejects it instead of dropping the tags. Read them back from `context.namedTags` on read and delivered events.
- Batches cannot combine non-empty named tags with any registered `eventSource` entry, even when the tags and registered source belong to different events. The client throws `NamedTagsWithRegisteredEventSourceNotSupported` before any RPC because the kernel's named-tag batch operation drops registered source routing ([kernel issue](https://github.com/Cratis/Chronicle/issues/4603)). Single `append` calls support this combination; batches with an empty `namedTags` array or without registered sources are unaffected.
- `eventLog.redact(sequenceNumber, reason)` and `eventLog.redactForEventSource(eventSourceId, reason, eventTypes?)` permanently rewrite an event's (or an entire event source's) content — a destructive GDPR/compliance erasure, never a field-level mask. Read [Event redaction](/chronicle/events/redaction/) before using them.
- `eventLog.getForEventSourceIdAndEventTypes(eventSourceId, eventTypes, ...)` and `eventLog.getFromSequenceNumber(sequenceNumber, eventSourceId?, eventTypes?)` read appended events back, filtered by event source and/or event type. Use [Getting events](/chronicle/events/getting-events/) when you need the events themselves rather than a read model.
- Route arguments on `getForEventSourceIdAndEventTypes` and `getTailSequenceNumber` do not default to the legacy `Default` route. An omitted dimension does not narrow the read, so it also returns the events the kernel routed for an append with no route options. Pass the dimensions explicitly to scope a read to one stream; see [Preserve existing append routes](./migrate-append-routing.md).
- `eventLog.getNextSequenceNumber()` returns the sequence number the next append will receive (`EventSequenceNumber.first` when the sequence is empty).
- `eventLog.completeStream(eventStreamType, eventStreamId)` permanently closes a non-default stream; further appends to it are rejected with a `StreamClosed` constraint violation. See [Closing streams](/chronicle/closing-streams/).
- `eventLog.appendOperations` is a hot, multicast `AsyncIterable` of every append this event log instance makes, together with its result. [Observing appends](/chronicle/events/observing-appends/) describes this client-side observation; it is not observer completion.
- `appendResult.waitForCompletion(timeoutMs?)` waits for every observer affected by an accepted append to catch up or fail. Pass `{ timeoutMs?, signal? }` instead to cancel the underlying wait RPC when the caller aborts; either the signal or timeout cancels it. The timeout defaults to 5 seconds. Timeout, cancellation, and RPC failures reject the wait; observer failures are returned in its completion result. For an unsuccessful append it resolves immediately with `isSuccess: true` and no failed partitions, because there is nothing to wait for. That is why you must check the append's own `isSuccess` first. See [Failed Partitions](./failed-partitions.md).
- `appendMany(events: EventForEventSourceId[], options?)` sends every `options.concurrencyScopes` label, including labels that are not append targets. A target without an explicit entry uses the shared `concurrencyScope` option. The kernel requires at least one event per batch; a scope-only batch is rejected.
- For [optimistic concurrency](/chronicle/events/concurrency/), use `EventSequenceNumber.beforeFirst.value` as `sequenceNumber` when a scope must assert that no matching event exists. It is sent as the wire `ExpectsNoMatchingEvent` flag, not as a sequence number; `EventSequenceNumber.unset.value` means no expected revision. On a kernel that does not support the flag, the check is skipped, so verify server compatibility before relying on this for a first append.
