# Projection materialization oracle

From the repository root, run `yarn install --immutable`, then `yarn oracle:check`. This requires the .NET SDK pinned by the repository-root `global.json` (10.0.401, no roll-forward). Ordinary `yarn test` does not require .NET. To inspect the compatibility boundary alone, run `dotnet run --project Tools/ProjectionOracle -- --smoke`. To intentionally replace committed expectations **after reviewing an engine upgrade or fixture change**, run `dotnet run --project Tools/ProjectionOracle -- --update` and inspect the diff. CI never updates them. The oracle pins `TZ=UTC` and the invariant .NET culture before loading the kernel, so date-time output does not depend on the host. The weekly NuGet probe skips prereleases and executes the fixtures against the latest stable package in a temporary project; drift and incompatible releases are reported without updating the pin or failing the scheduled job.

The oracle pins `Cratis.Chronicle.Testing` **19.26.2** (Chronicle commit `1f8d832`) in `ProjectionOracle.csproj`. At check time, it compares each fixture's engine version and commit prefix with the loaded package assembly's informational version; the installed contracts package version and descriptor SHA-256 are checked against every fixture too. The package contains Core, Concepts, Contracts, Grpc, Infrastructure, Storage and Storage.InMemory under `lib/net10.0`, but only Testing is exposed under `ref/net10.0`. The project adds aliased compile references to **those same packaged DLLs** using `GeneratePathProperty` and a lockfile, not to a separate kernel checkout. The one internal access is `ProjectionDefinitionBridge`: it reflects the package's transport-to-kernel `ToChronicle` converter and asserts its exact parameter/return signature on every run. This is version-fragile; do not silently fall back to a copied converter. The packaged Core's generated type discovery also requires the matching `Cratis.Arc` runtime assembly. The package embeds Roslyn 5.9 while a transitive dependency exposes a Roslyn 5.0 compile asset, so the project excludes that older compile asset.

The isolated constraint fixtures (`constraints-isolation.json`, `constraints-key-domain.json`, `constraints-property-lifecycle.json`, `constraints-property-covered-removal.json`, `constraints-event-type-siblings.json`, `constraints-event-type-cycles.json`, `constraints-composite.json`, and `constraints-ignore-casing.json`) explicitly select their unscoped client definitions, declare all event schemas and their definition provenance, and assert the effective kernel definitions installed by the packaged testing adapter (ordered event properties, scope, removal and casing). The lifecycle fixtures prove owner-based replacement/removal, fieldless removal events, covered-and-removal validation, and the fact that property claims are never released during whole-batch validation; their accepted history includes hashes for every event. The event-type fixtures install one explicit definition for the complete covered type set (not merged .NET class attributes), include alternative removers and a covered-and-removal event, and capture single and atomic batch cycle releases and rejections. The composite fixture installs multi-property definitions in declared property order (composite events use a `values` object instead of `value`); the oracle passes the order and the fixture's `ignoreCasing` flag through, asserts both on the installed kernel definition, and never joins, folds or compares values itself. They pin the generated `events_constraints.ts` descriptor in addition to the event-sequence descriptor. Each single or batch operation captures the mapped client result, raw contract violations on rejected appends, full accepted content/routes/hashes, and next sequence; rejected operations assert unchanged history and sequence. Only rejected appends are resent to the packaged kernel service to capture its raw response. The original `constraints.json` increment-4 regression fixture keeps its previous runner and meanings. These original isolated fixtures cover unscoped constraints. The separate `oracleGuard` fixture for unsupported key conversions is deferred; the TypeScript specs reject those inputs but do not claim packaged-kernel behavior for them. Add new fixture names to `Program.Main`'s required list so `oracle:check` cannot pass without them. `--update-events` rewrites all event fixtures; inspect its diff and retain unrelated fixtures unchanged.

`constraints-field-types.json` sends literal JSON directly through the packaged single/batch services, without .NET client serialization erasing Guid casing, numeric spelling or date offsets first. Its runner asserts each installed unscoped, single-property, single-event-type definition and records and asserts the effective property schema read through kernel storage. The numeric cases cover both `number/double` and exactly the unformatted `number` property emitted by TypeScript `@field(Number)` and `ConceptAs<number>`. The packaged testing adapter's registration methods are no-ops, so the runner replaces the number case's input schema in its scenario-local discovered-schema catalog before appending. That additional reflected catalog access asserts its exact packaged shape and fails closed on drift; kernel conversion and constraint evaluation remain unchanged. Supported cases prove dashed Guid comparison and lowercase violation details, safe-integer boundaries, `1` versus `1.0`, same-source replacement, batch rejection, unchanged history and next sequence, and stored hashes. Separate `oracleGuard` cases capture fractional/exponential and unsafe-integer formatting, raw negative zero (which TypeScript's production serializer emits as `0`), and `DateTime` keys with the installed `string/date-time` schema that TypeScript emits for `Date`: equivalent instants with different offsets collide, and fractional seconds disappear from keys/details. This is not `DateTimeOffset` / `date-time-offset` evidence. Those guards do not authorize general numeric or date-key support. Raw history reads expose kernel-normalized content, not the .NET client's typed deserialization. TypeScript scenarios preserve client-serialized payloads; their deterministic hashes outside the proven domain are scenario-local, and observed Hash projections reject such schemas.

`constraints-scopes.json` adds isolated cases for all seven nonempty combinations of source-type, stream-type and stream-ID scopes: case-sensitive single-string property keys, singleton event-type constraints and two-type/two-remover cycles. It captures exact/default/empty routes, selected versus unselected dimensions, case-sensitive routing, scope-local replacement/removal, batch rollback and both TypeScript batch overloads. Each case installs its definition alone. Delimiter aliases are `oracleGuard` cases: property scopes flatten unescaped strings while event-type scopes compare tuples; TypeScript scenarios continue rejecting those route characters.

The scope adapter is the fixed **packaged** testing adapter in 19.26.2, not a replacement validator. `scope-wire.mjs` uses the pinned TypeScript contract encoders for scope definitions and every append request. The oracle decodes those protobuf bytes before constructing the client scope, asserts selected `*` versus omitted/null scope members, and checks the effective installed kernel definition (including scope). It runs every scoped operation twice in independent packaged scenarios: once through the .NET client and once through the decoded TypeScript request. Success, sequences, errors, complete content/routes/hashes and next sequence must agree. Raw violations come from the wire scenario. In particular, an empty TypeScript string is omitted on the wire; assigning `""` to a nullable .NET contract member is not used as evidence of that omission. Routing precedence is prepared explicitly in the wire encoder and checked against production TypeScript preparation by the scenario specs; the oracle does not implement constraint evaluation.

The fixtures are checked against the generated `@cratis/chronicle.contracts` 19.26.2 wire layout, including key/value **arrays** for event-type dictionaries. Their definitions were hand-written against the contract version recorded in each fixture's `definitionSource` (19.6.1 for the original projection fixtures) before the shared `ProjectionDefinitionCompiler` landed, then converted by the packaged Grpc converter and executed by the packaged engine; see `definitionSource` in each fixture. The descriptor SHA-256 of the installed generated `projections.ts` file detects TS contract drift. Each fixture records its format version, a `kind` (`kernelSemantics` for kernel behavior a TypeScript evaluator must reproduce, or `oracleGuard` for kernel behavior outside the phase-1 evaluator boundary or the oracle's own fail-closed boundaries; the evaluator asserts rejection rather than comparing snapshots), engine version/commit, contract version/hash, read-model and participating event schemas, explicit ordered event contexts (lossless string sequence numbers), wire definition and per-event expectations. Unknown event/context and wire fields fail closed. Root `Join` entries and `All` mappings are read as strict packaged contract definitions; `SubscribesToAllEvents` is passed to the packaged converter and factory, not simulated by the runner. Children are read one level deep with `From` and `RemovedWith` only; any other child operation fails closed. Contexts can supply `eventSourceType`, `eventStreamType`, `eventStreamId`, `correlationId` (GUID), `causation` (`occurred`, `type`, string `properties`), `causedBy` (`subject`, `name`, `userName`, recursive `onBehalfOf`), `tags`, `hash` and `subject`; omitted values use the kernel defaults. Events within one fixture must share an event store and namespace; omitted values use the kernel's `NotSet` sentinels. For a failing final step, put `expectedError: { "type": "...", "message": "..." }` on the event; the corresponding expected snapshot includes `error` beside `engineState` and `publicRead`. An unexpected exception fails the run rather than producing an expected error.

The runner creates a real `ProjectionFactory` projection and calls the public `ProjectionPipeline.Handle` with the complete production step sequence: `ResolveKey → SetInitialState → DecryptInitialState → HandleEvent → EncryptChangeset → StoreFutures → ResolveFutures → SaveChanges`. Events are appended to the in-memory sequence before handling. Strict proxies guard the factory lookups, compliance and replay-cache dependencies, and unsupported futures operations. The one permitted futures call is `GetFutures()`: the production tracker probes durable storage once on its first event, so the empty in-memory store returns no futures. Plain schemas do not call compliance. It skips unrelated events as the production subscription filter does. Snapshots contain the sink's **engine state**, including `__initialized` and explicit nulls, alongside the schema-normalized **public read** produced by the same `ExpandoObjectConverter.ToJsonObject` used by `ReadModels.GetInstanceById`. Keys absent from `publicRead` mean no materialized instance; missing fields and explicit null fields remain distinguishable in `engineState`. The separate `ProjectionReadModelProcessor` replay loop in Chronicle.Testing is never called.

For root joins, the production factory wires `ResolveJoin` to each `From` clause that maps the joined property, including inferred AutoMap. It reads the latest prior source event from the packaged event-sequence store. Later join-only events create `Joined` changes against empty state; the packaged sink applies these to every matching existing root. No joined read-model row, custom join-state store or durable future is involved. The TypeScript evaluator keeps a replay-local latest-event lookup, not accumulated joined properties. The relevant pinned sources are [ProjectionFactory](https://github.com/Cratis/Chronicle/blob/v19.26.2/Source/Kernel/Core/Projections/Engine/ProjectionFactory.cs), [ResolveJoin](https://github.com/Cratis/Chronicle/blob/v19.26.2/Source/Kernel/Core/Projections/Engine/ProjectionEventContextExtensions.cs), [SetInitialState](https://github.com/Cratis/Chronicle/blob/v19.26.2/Source/Kernel/Core/Projections/Engine/Pipelines/Steps/SetInitialState.cs) and [InMemorySink](https://github.com/Cratis/Chronicle/blob/v19.26.2/Source/Kernel/Storage.InMemory/Sinks/InMemorySink.cs).

| `null-accumulator` | `oracleGuard` — a cleared, present accumulator throws instead of behaving like an absent accumulator. Definitions combining clearing and arithmetic reject before replay. |

| `joins-root-key-collision` | A join source ID equal to an unrelated root ID does not update that root or create another row; only the joined property selects roots. |

| `children-identified-removed` | Fluent `identifiedBy`/`usingKey` children with no root `From`: the first child-only event creates an uninitialized parent that the next event initializes; the identifier is set from the child key; `RemovedWith` removes the matching child, ignores unknown keys, and creates an empty uninitialized parent for an unknown parent key. |

| `children-untyped-items` | The legacy-decorator `@childrenFrom` options form without `childType` or element-type metadata retains an untyped `{ "type": "object" }` item schema: AutoMap maps nothing and only the identifier is stored. Pass `childType` to map the child's properties. |

This is a **materialization proof**, not a live-kernel storage oracle: no Orleans scheduling, protected-field compliance/decryption, stored futures, nested or joined child projections, MongoDB BSON conversion or Docker-backed keyed read is exercised. In particular, the in-memory sink writes its own `id` property, whereas a persistent sink can use `_id`. Arithmetic support remains limited to root source-ID projections with number/double or int32 accumulators and direct numeric event-property operands. Uint32 targets, nonnumeric/nullable schemas, text assignments into accumulators, clearing, other numeric formats, dynamic/context operands, custom/constant keys, arithmetic with children or joins and `fromEvery` remain rejected. All-event and from-every definitions remain rejected before replay by the TypeScript evaluator, including empty all-event subscriptions. Their fixtures prove the packaged kernel's behavior, not evaluator support. Children support is unchanged. Joins are limited to one root join event type, source-ID keys, a direct non-identifier join target populated by a `From` clause, plain string read-model properties and direct plain string event-property assignments. Multiple joins, empty effective mappings, join-only projections, initial state, other schemas/expressions, overlapping `From`/`Join` events or destinations, mutating the join target, child joins, `removedWithJoin` and joins combined with children or arithmetic reject before replay. Live-kernel differential coverage for storage-sensitive cases belongs to later increments. Keep the package pin and expectations together when upgrading.
